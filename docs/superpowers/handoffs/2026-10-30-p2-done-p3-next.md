## 1. 产品与范围

- **是什么**：内部自用的销售 CRM，团队 5–20 人。
- **三件事的进度**：① 管理客户资料（P1 完成）② 管理销售机会（**P2 完成**）③ 管理销售人员跟踪客户的记录
  （**P3**）。
- **形态**：Web 应用，PC 与手机浏览器自适应。技术栈：FastAPI + SQLAlchemy 2.x（同步）+ PostgreSQL 16 /
  React 18 + Vite 5 + TS + Tailwind 3。方案 A 模块化单体。
- **里程碑**（spec §11）：P1 客户/权限 → **P2 机会/看板/阶段历史** → **P3 跟进/待办/首页三块** →
  P4 公海池 → P5 报表/Excel 导入 → P6 部署上线。spec 原话：**P1–P3 完成即可投入日常使用**。
- **P2 之后能回答什么**：这个客户在谈哪几单、每单谈到哪一步、多少钱、赢单率多少、上次阶段什么时候变的。
  **还不能回答**：上次聊了什么、下次找谁、今天该做什么（那是 P3）。

## 5. 已定的架构约定增量（P3 必须沿用）

1. **机会作用域的唯一构造点**：`backend/app/modules/opportunities/service.py` 的
   `_visible_conditions(actor, *, customer_id=None)`。它内部用
   `Opportunity.customer_id.in_(customer_query(actor).with_only_columns(Customer.id))` 表达可见性，
   并统一过滤 `deleted_at IS NULL`。**P3 的 activities / follow_ups 读取必须照这个模式写**，
   不许自己拼可见性；"我的待办"按 spec §3.9 是 `join customers on owner_id = me`，而不是给待办加负责人字段。
2. **写前必过 `assert_customer_writable(customer, actor)`**（公海客户对 sales/manager 只读）。
   机会的写入路径统一经 `_writable_customer(db, actor, customer_id)`。
3. **阶段变更只能走 `POST /opportunities/{id}/stage`**：`PATCH` 的 schema 里没有 `stage`（`extra="forbid"` → 422），
   所以 `stage_histories` 不可能被绕过。P3 的时间线要读这张表，**不要**另建"阶段变更记录"。
4. **`sync_opportunity_owner(db, *, customer_id, owner_id)` 已就位，不 commit**：
   P4 的领取/分配/转移必须在**同一个事务**里调用它（只改未关闭且未软删的机会，已关闭的保留原负责人）。
   绝不允许 P4 自己另写一遍这套条件。
5. **派生字段的预加载**：`Opportunity.customer / owner / lost_reason` 全是 `lazy="raise"`。
   任何读机会的新查询都要 `joinedload`（服务层已有 `_with_relations` / `_load_full`），
   漏了会立刻抛 `InvalidRequestError`（故意 fail-loud，不是 N+1）。
6. **金额是定点字符串**：wire 上 `"1234.50"`，前端 `formatAmount` 格式化，**不做** `Number()` → `toFixed()`
   往返；日期列（`date`）用 `formatDateOnly`，`datetime` 列要先按 `Asia/Shanghai` 换算。
   P3 的时间线同样要处理（`activity_at` / `changed_at` 都是 `timestamptz`）。
7. **赢单率的两个真值**：`win_rate` 列非空 = 手工值，空 = 跟随 `STAGE_WIN_RATES`；响应给
   `win_rate`（生效值）+ `win_rate_manual`。改阶段不覆盖手工值。
8. **导航与路由**：`AppShell` 的 NAV 里「机会」带 `end: true`（否则看板页会让两项同时高亮）。

## 7. 已知限制与债务（P2 执行过程中真实产生的）

按"何时处理"分组。**这些不是猜测，是 P2 期间实测/读代码确认的事实。**

### 7.1 P3 就应该决定或修掉的

| # | 债务 | 细节与代价 | 建议何时处理 |
|---|---|---|---|
| 1 | **改已赢/已输机会的 `amount` 不受限制** | `PATCH` 对终态机会同样接受 `amount`。`stage_histories.amount_snapshot` 记的是变更当刻的值，所以事后改金额不会改历史——但报表若读 `opportunities.amount`，历史业绩就会被事后篡改。 | **P3 写报表口径前定死**：成交额读 `amount_snapshot`（推荐）还是 `amount`，并写进 P3 计划；若选后者，P3 需禁止改终态机会金额。 |
| 2 | **客户被软删后，其机会对所有角色（含 admin）不可见，详情返回 403** | 机会可见性经 `customer_query(actor)`，客户软删即过滤；`get_opportunity` 于是走 403「无权查看该机会」。字面合规格（"记录存在且未删 → 403"），但 admin 看到"无权"会误导排障。 | **P3 统一文案或改 404**（越权 403 / 记录没了 404 的口径要在 P3 定，时间线也会踩到）。 |
| 3 | **删除机会不写审计** | 软删只写 `opportunities.deleted_at`，`stage_histories` 看不出谁删的、何时删的。 | P3 若做时间线可见"机会被删除"的痕迹，需补 `audit_logs`（spec §3.13）或至少记一条 history；否则留给 P4/P5 审计。 |
| 4 | **客户详情机会区最多显示 50 条** | 前端固定 `page_size: 50`，且**没有**"仅显示前 N 条"提示（看板有，详情页没有）。单客户机会超过 50 条时静默截断。 | P3 改客户详情页时顺手加"共 N 条 / 查看全部"或分页。 |
| 5 | **管理员在公海客户详情看得到「+ 新建机会」，但保存必 400** | 客户详情页的 `writable` 对 admin 恒为 true（P1 口径：公海只读只约束 sales/manager），而机会要求客户有负责人，所以 admin 点进去必然吃 `客户未分配负责人…`。 | P4 做领取/分配后自然消解；若 P4 之前要打磨，前端按 `owner_id === null` 禁用按钮并给出说明。 |

### 7.2 P4（公海领取/分配/转移）必须处理的

| # | 债务 | 细节与代价 | 建议何时处理 |
|---|---|---|---|
| 6 | **`sync_opportunity_owner` 不校验负责人有效性** | 它只 `UPDATE opportunities SET owner_id=...`（未关闭且未软删），`owner_id` 若指向停用用户/不存在用户会直接撞 FK 或留下"机会挂在停用账号上"。它**不 commit**（设计如此：要与客户归属同事务）。 | **P4 在同一事务里先 `get_user` 校验 `status` / 部门，再调用**；不要把校验塞进这个函数（它没有 actor 上下文）。 |
| 7 | **字典没有软删列，`active=false` 是唯一"停用"** | 若 P5 的字典管理做"删除"，硬删会让历史机会的输单原因分组整块消失（`lost_reason_id` 悬空/级联风险）。 | **P5 做删除前先补 `deleted_at`**（或明确只允许 `active=false`，接口不提供 DELETE）。 |
| 8 | **停用的输单原因不能再被新输单引用** | P2 在 `change_stage` 里对 `active=False` 直接 400「该输单原因已停用，请选择其他原因」；这是 `active` 字段唯一有执行力的地方。 | **P5 加字典管理时必须保留这条语义**（否则"停用"变成纯展示，报表口径会被悄悄污染）。 |
| 9 | **种子对输单原因名称有硬依赖** | `scripts/seed.py` 用**名称**建 `{name: reason}` 映射再按名字取 id（`reasons[spec.lost_reason]`）；管理员一改名，重跑种子就 `KeyError`。另外种子**按名判重、不改既有项**，手工建的同义行会留下两条语义重复。 | **P5 落地字典管理时改成"找不到就 skip + 警告"**，不要让种子炸掉。 |
| 10 | **种子机会的阶段历史时间戳全是执行时刻** | 种子逐阶段调用 `change_stage`，所有 `changed_at` 是播种那一刻；漏斗/成交周期在演示数据上显示 0 天。 | 种子只为冒烟，不代表真实历史。P5 报表验收要用真实操作造数据，或给种子加"回填时间"的开关。 |

## 8. P3 范围（spec 已定，不需要重新设计）

**两张表**（spec §3.8 / §3.9）：`activities`、`follow_ups`。

**核心规则**
- `activities`：`customer_id` 必填，`contact_id` / `opportunity_id` 可空；`type` 六值
  （call/visit/wechat/email/note/other）；`content` 必填；`activity_at` 可过去；索引
  `(customer_id, activity_at desc)`、`(created_by, activity_at)`。
- `follow_ups`：**不设负责人字段**，"我的待办" = join `customers.owner_id`；`status`
  pending/done/cancelled；`due_at` 含时分；索引 `(status, due_at)`、`(customer_id, status, due_at)`。
- `last_activity_at` 只在**新建 activity** 与**领取/转移**时更新（spec §3.3 三条规则），
  补录历史跟进时取 `max(原值, activity_at)`；**改阶段、改联系人一律不碰**（P2 已用测试钉住）。
- 写跟进时可选"下次跟进"→ 同一事务建 `follow_ups(pending)`；完成待办可"顺便写条跟进"
  （spec §4.5）。逾期 = `due_at < 今天 00:00 (Asia/Shanghai)` 且 `status='pending'`。
- **`GET /customers/{id}/timeline`**：合并 `activities`、`stage_histories`（该客户名下**所有机会**）、
  `owner_change_logs` 三类，按时间倒序，游标 `(occurred_at, type, id)`。
  注意三张表的时间列名不同（`activity_at` / `changed_at` / 变更日志的时间列），且**已软删的机会**、
  被停用用户的操作要不要出现在时间线上，spec 未定——P3 计划里要写清楚。
- **首页 `/`** 三块（spec §6.1）：今日待办 / 已逾期 / 即将进公海。第三块的"即将进公海"依赖
  `pool_rules`（P4），P3 只能给占位或按下发的规则先写死，需在计划里定。
- **移动端**（spec §6.3）：右下角全局悬浮按钮「+跟进」；详情页时间线优先于字段区。

**接口**：`CRUD /activities`、`CRUD /follow_ups` + `POST /follow_ups/{id}/done` +
`GET /customers/{id}/timeline`。

**页面**：`/`（首页三块）、客户详情页右栏时间线 + 顶部"写一条"、跟进/待办弹窗；移动端悬浮按钮。

**P3 明确不含**：公海池与领取/回收（P4）、报表（P5）、Excel 导入（P5）、管理后台（P5/P6）。

**建议拆 8–10 个任务**：activities 模型+迁移 → follow_ups 模型+迁移 → 服务层（作用域、last_activity_at 规则）
→ 接口层 → timeline 合并读 → 首页三块 → 客户详情时间线 + 写跟进 → 待办完成闭环 → 移动端悬浮按钮 → 端到端与验收。

## 9. 开工前待决（P3 计划里必须写清的 5 项）

1. **时间线的边界**：已软删的机会 / 已停用用户 / 已删除联系人，在时间线里显示还是隐藏？
   隐藏会让"阶段变过"看不出来，显示需要 join 已删行（绕过软删过滤），两者都要写进计划。
2. **首页"即将进公海"**：`pool_rules` 属 P4，P3 期间用什么规则（写死 30 天？占位空态？）。
3. **待办的可见性**：spec 只说"跟着客户走"，但主管看本部门时能不能看到下属的待办？
   （建议：与客户可见性一致，主管能看到本部门客户的待办，但"我的待办"仍按 `owner_id = me`。）
4. **成交额口径**：读 `opportunities.amount` 还是 `stage_histories.amount_snapshot`（见 §7.1 #1）。
   这影响 P5 报表，P3 的 timeline 也会展示金额，先定下来省得返工。
5. **跟进记录的编辑/删除权限**：销售能否改别人写的跟进？主管能否删？spec 未定，
   建议"本人可改删、主管可删本部门"，但要在计划里显式裁定。

## 10. 工作方法论与纪律（照抄即可，别重新发明）

- **执行方式**：控制器（Lead）派单 → 实现者 → 独立评审者 → 修复轮 → 下一个任务。**一次只有一个实现者**
  （共享 git 索引）。实现者/评审者一律不得再派子代理。
- **TDD 纪律**：先写失败测试并确认它真的红 → 实现 → 绿 → 提交。每个后端任务必须包含
  "改坏→红→改回→绿"的变异验证，把红/绿原始输出写进报告。**前端无测试框架**，
  红/绿由 `tsc --noEmit` + `vite build` 承担（外加手测清单）。
- **验收口径**：测试必须压真实 PostgreSQL 语义；**只断言状态码的测试不接受**（要断言 `code`/业务字段）；
  硬造假用户/假场景去测未实现的功能不接受。**每次要求"全量验证"时真跑并把输出尾部贴进报告。**
- **派单纪律**：涉及既有 schema 的字段必须**从文档引用**，禁止凭记忆列举；派单里要写"若我的说法与文档不符，
  请直接质疑"。
- **范围蔓延要挡**：判定标准是"spec 明文要求"，不是"看起来有用"。
- **账本**：每条裁定写进 `.superpowers/sdd/<plan>/progress.md`；收尾时蒸馏进 `docs/`。
- **汇报习惯**：长任务期间静默不超过约 10 分钟。
