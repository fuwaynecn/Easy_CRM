## 3. P3 范围（spec 已定，不需要重新设计）

**两张新表**（spec §3.8 / §3.9）

- `activities`：`customer_id` 必填，`contact_id` / `opportunity_id` 可空；`type` 六值
  （call/visit/wechat/email/note/other）；`content` 必填；`activity_at` 允许补录过去；
  索引 `(customer_id, activity_at desc)`、`(created_by, activity_at)`。
- `follow_ups`：**不设负责人字段**——"我的待办" = join `customers.owner_id`；
  `status` pending/done/cancelled；`due_at` 含时分；索引 `(status, due_at)`、`(customer_id, status, due_at)`。

**核心规则**

- `last_activity_at` 只在三个点更新（spec §3.3）：**新建 activity**、**领取**、**转移**。
  补录历史跟进取 `max(原值, activity_at)`；**改阶段、改联系人一律不碰**（P2 已用测试钉死，别破坏）。
- 写跟进时可选"下次跟进" → 同一事务建一条 `follow_ups(pending)`；
  完成待办可"顺便写条跟进"（spec §4.5）。
- 逾期 = `due_at < 今天 00:00 (Asia/Shanghai)` 且 `status='pending'`。
- `GET /customers/{id}/timeline`：合并 `activities` + 该客户名下**所有机会**的 `stage_histories` +
  `owner_change_logs`，按时间倒序，游标 `(occurred_at, type, id)`。
  三张表时间列名不同（`activity_at` / `changed_at` / 变更日志的时间列）。

**接口**：`CRUD /activities`、`CRUD /follow_ups` + `POST /follow_ups/{id}/done` + `GET /customers/{id}/timeline`。

**页面**：`/` 首页三块（今日待办 / 已逾期 / 即将进公海）、客户详情页右栏时间线 + 顶部「写一条」、
跟进/待办弹窗、移动端右下角全局悬浮「+跟进」（spec §6.3）。

**P3 明确不含**：公海池与领取/回收（P4）、报表（P5）、Excel 导入（P5）、管理后台（P5/P6）。

**建议拆 8–10 个任务**：activities 模型+迁移 → follow_ups 模型+迁移 → 服务层（作用域、`last_activity_at` 规则）
→ 接口层 → timeline 合并读 → 首页三块 → 客户详情时间线 + 写跟进 → 待办完成闭环 → 移动端悬浮按钮 → 端到端与验收。

## 5. 纪律（照抄，别重新发明）

- 控制器（Lead）派单 → 实现者 → 独立评审者 → 修复轮 → 下一个任务。**一次只有一个实现者**（共享 git 索引）。
  实现者/评审者一律不得再派子代理。
- **TDD**：先写失败测试并确认它真的红 → 实现 → 绿 → 提交。每个后端任务都要"改坏→红→改回→绿"的变异验证，
  红/绿原始输出写进报告。**前端无测试框架**：红/绿 = `tsc --noEmit && vite build`，外加手测清单。
- **测试口径**：压真实 PostgreSQL；**只断言状态码不接受**（要断 `code`/业务字段）；不许造假场景去测没实现的功能。
  每次"全量验证"都要真跑并贴输出尾部。
- **派单纪律**：涉及既有 schema 的字段必须**从 spec 引用**，禁止凭记忆列举；派单里写"若我的说法与文档不符，请直接质疑"。
- **范围蔓延判定标准**是"spec 明文要求"，不是"看起来有用"。
- **账本**：`.superpowers/sdd/<plan>/progress.md` 记每条裁定（格式 `Ruling: <结论> — <理由> — <错的代价>`），
  收尾蒸馏进 `docs/`。
- **汇报**：长任务静默不超过约 10 分钟。
