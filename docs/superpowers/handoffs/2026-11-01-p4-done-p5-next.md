## 3. 既有约束（写 P5 代码前必读）

- **可见性一律从 `customer_query(actor)` 起**：公海可读不可写（admin 例外）。别在新查询里
  自己拼 `owner_id == actor.id`。
- **所有者变更统一写两张日志**：`owner_change_logs`（含 `action`、from/to、reason）+
  `audit_logs(action="transfer")`。`action` 取值受数据库 CHECK 约束：
  `claim|recycle|assign|transfer|release`。
- **`assign` 与 `transfer` 的区别是「原来有没有人」**：`from_owner_id is None` → `assign`，
  否则 `transfer`。P5 做报表按动作统计时不要混。
- **claim/assign 会 `sync_opportunity_owner` 同步未关闭机会；release/recycle 故意不动**（裁定 2）。
- **`last_activity_at` 只有 claim 重置**；assign/transfer/release/recycle 都不碰。
- **时间线故意不过滤软删**：已删联系人/机会/停用账号照常出条目，靠 `*_deleted` /
  `operator_disabled` 标记。新增时间线来源必须保留 `deleted_at` 语义与游标类型（`CURSOR_TYPES`）。
- **回收用事务级 advisory lock**：拿不到锁直接回滚调用方事务并返回 0。P4 的调用方是
  scheduler 新 session / `scripts/recycle_now` / 测试，都没有未提交业务写；
  **不要把 `recycle_customers` 嵌进别的事务中间调用**。
- **规则读走 `load_pool_rules(db)`**：行被删时回落默认值，不要直接 `SELECT pool_rules` 后假定非空。
- **调度是进程内 APScheduler**：`app/scheduler.py` 注册 02:00 回收、02:10 部门一致性；
  `settings.scheduler_enabled` 控制启停，测试 `conftest.py` 在 import 后立即置 False。
  多实例下**只有 02:00 回收任务**取事务级 advisory lock 兜底；**02:10 部门一致性任务不取锁**，
  多实例会并发执行（它是幂等的，但没有串行化）。没有选主、没有持久化 job store。
- **E2E 的时间线顺序断言**（`["release","transfer","claim"]`）依赖三次独立 HTTP 事务的
  `created_at`/`id` 递增；串行请求下成立，并发化后要重新审这条断言。
- **前端没有单测框架**：前端验收 = `tsc --noEmit && vite build` + 源码检查 + 人工浏览器。

3. 释放：仍用 `admin`（客户已归华南，华东的 `boss` 释放会 403）→ 回到公海。

要演示「主管本部门分配」，需先用 `admin` 把客户分给另一个华东销售，或给种子再加一个华东销售。

**注意 `python -m scripts.recycle_now` 会真的改开发库**：
它会按当前规则把超期客户挪进公海，想保留演示数据就别在 `easycrm` 上跑。
