## 1. 交付摘要

### 1.1 后端新增端点

报表全部只读，无写路径；`user` 为 `CurrentUser`（任何登录角色）。

| 方法 / 路径 | 说明 |
|---|---|
| `GET /api/v1/reports/funnel` | 漏斗：六个阶段的当前机会数与最新阶段历史金额快照；阶段顺序固定 `contact…lost` |
| `GET /api/v1/reports/win-rate` | 赢单率：期间内 `won_at` 到达 vs lost 历史到达；`rate = won/(won+lost)`，无分母时 `null`；附按部门拆分 |
| `GET /api/v1/reports/cycle` | 平均成交周期：`won_at − created_at` 的均值（天，一位小数）；附按负责人、按上海月份 |
| `GET /api/v1/reports/performance` | 销售业绩：最后一条 won 历史的 `amount_snapshot` 汇总；按月/按人 |
| `GET /api/v1/reports/activities` | 跟进量：期间 `activity_at` 条数，`granularity=day\|week`，空桶补 0；按作者 |
| `GET /api/v1/reports/lost-reasons` | 输单原因：期间 lost 历史条数 + 快照金额，按原因分组 |
| `GET /api/v1/reports/competitors` | 竞争对手：`competitor` 按顿号拆分，同机会多对手分别计，含赢单/输单/赢率 |
| `GET /api/v1/imports/{kind}/template` | 下载客户导入模板（`kind` 仅 `customers`）；`ManagerOrAdminUser` |
| `POST /api/v1/imports` | 上传 `.xlsx` + `kind=customers`；解析 + 逐行校验，落文件与 `import_jobs`，返回 201；`ManagerOrAdminUser` |
| `GET /api/v1/imports/{id}` | 查询导入任务；admin 任意、manager 仅自己创建的（否则 404）、sales 403 |
| `POST /api/v1/imports/{id}/commit` | 确认写入：重新解析校验，单事务建客户 + 写 1 条审计；失败整体回滚 |

报表查询参数：六个带区间的端点（win-rate / cycle / performance / activities / lost-reasons /
competitors）接受 `date_from` / `date_to`（必须同时给），缺省为**上海时区本月 1 日到今天**；
`activities` 另有 `granularity`（`day` 默认 / `week`，其他值 400 `invalid_value`）。
`funnel` 无区间参数（看当前在途与终态分布）。

权限矩阵见 `p5-acceptance.md` §5；一句话：**报表 admin 全公司 / manager 本部门 / sales 本人，
按机会负责人当前部门归属，不复用 `customer_query`；导入只给 manager 及以上，manager 的负责人
限本部门，sales 一律 403。**

另有两条实施口径，改之前先想清楚：

- **`changed_at` 只做区间归属，绝不用于挑「最新阶段」**：最新一行按 `id` 取（`stage_histories`
  只追加）。用 `changed_at` 排序会被测试夹具/将来迁移回填的时间打乱。
- **commit 是单事务**：客户 + 审计 + job 状态一起提交；任何一步失败整体回滚，再把 job 用独立
  事务标 `failed`。不要改成「逐行提交」或「部分成功」。

## 3. 既有约束（改 P5 代码前必读）

- 报表端点**只读**：不写 `stage_histories`、不改 `opportunities`。P5 没有新增写路径。
- 报表不复用 `customer_query`（公海客户可见会重复计数）；`activities` 按作者部门、其余按机会
  负责人部门——两者**故意不同**，别统一。
- 导入是**两阶段**：上传只解析+校验+落文件（`settings.import_dir/{job_id}.xlsx`，存上传原文），
  commit 重新解析校验后再写；不要信上传阶段的校验结果。
- 导入**不更新**已有客户：重名（`normalize_name` 归一化后）一律跳过，不覆盖。
- 导入的负责人必须是 **active 且有部门**的用户；manager 只能导本部门负责人。
- 导入写客户时 `department_id` 取负责人部门、`created_by` 取操作人（不是负责人）；
  **不走** `record_owner_change`（全新建，没有「原负责人」）。
- 审计只写一条 `action="import"`（`entity="imports"`，`after_json` 五个字段：
  `kind/file_name/total_rows/success_rows/skipped_rows`），不要逐行写。
- 前端权限只是隐藏：`/import` 的 `Navigate` 与 NAV 过滤都不是权限，后端 `ManagerOrAdminUser`
  才是。
- 前端无单测：验收 = `tsc --noEmit && vite build` + 源码检查 + 人工浏览器。

## 6. 已知限制（与 `p5-acceptance.md` §6 同一份，不要另写一套）

1. **报表金额是时点快照**：读 `stage_histories.amount_snapshot`；赢单后单独改金额、不换阶段，
   报表不变（也不会产生历史）。这是 P3 裁定，不是 bug。
2. **部门按当前负责人回算**：转岗后历史业绩会跟着人走；没有历史部门快照。
3. **重开机会不计入原赢单期间**：重开会清 `won_at`，所以它不再算期内赢单。
4. **竞争对手按顿号拆分**：同一机会多个对手分别计入，金额合计可大于机会总额。
5. **导入只支持客户、只支持 `.xlsx`、只新建不更新、不导出**：单次 5000 行 / 5MB。
6. **导入跳过重名不返回对方 id/名称**（避免越权枚举）；跳过数量只有计数。
7. **无站内信/邮件通知**；通知与多实例调度留给 P6。
8. **前端无单测**：`tsc --noEmit && vite build` 是唯一门禁；375px 与空态靠人工。
9. **`commit` 没有并发锁**：同一 job 被两个请求同时 commit 时，没有行锁/幂等键；前端在
   pending 时禁用按钮，但**API 客户端必须自己避免并发 commit**。延迟到 P6。
10. **损坏/丢失文件失败只记 `error_rows=1`**：上传阶段的 `total_rows` / `skipped_rows` 保留，
    前端会同时看到「总行数 N、错误 1 行」，这是刻意的（重传前保留统计），不是丢数据。
11. **校验是同步的**：上传在请求里完成解析与逐行校验（5000 行级别可接受），前端**没有轮询**；
    `getImportJob` 是为将来轮询预留的导出，目前页面未使用。
12. **页面 375px 只覆盖了公海（P4）、报表与导入（P5 运行时）**：登录页、客户列表、机会列表
    本次没有重新量测；报表/导入的空态没有浏览器实证。P6 补。

## 8. 不要做什么

- **不要改报表金额口径**：不要为了「和机会列表一致」把 `amount_snapshot` 换成
  `opportunities.amount` 现值——这会把历史成交额改写成现值，且让赢单后改金额的历史丢失。
- **不要给导入加部分提交**：commit 必须整体成功或整体回滚；失败行不能「先写一半」。
- **不要让 sales 进导入**：模板、上传、查询、commit 四个入口都是 `ManagerOrAdminUser`；
  前端的隐藏/跳转不是权限，别只在页面上加限制。
- **不要给报表套 `customer_query`**：公海客户可见，会让同一条机会在每个部门重复计数。
- **不要把报表做成写路径**：P5 报表全只读，不能顺手写 `stage_histories` 或改机会。
- **不要撤 `skipped_rows`**：spec 要求记录跳过，塞回 `error_rows` 会把「跳过」显示成「失败」。
