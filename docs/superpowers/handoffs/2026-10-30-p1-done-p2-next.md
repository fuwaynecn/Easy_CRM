## 1. 产品与范围

- **是什么**：内部自用的销售 CRM，团队 5–20 人。
- **用户最初的三件事**：① 管理客户资料 ② 管理销售机会 ③ 管理销售人员跟踪客户的记录。
  - P1 只做了 ①（外加联系人、登录/用户/部门、权限）。
  - ② 属 P2，③ 属 P3。
- **形态**：Web 应用，PC 与手机浏览器自适应（不做原生 App）。
- **技术栈**：FastAPI + SQLAlchemy 2.x（同步）+ PostgreSQL 16 / React 18 + Vite 5 + TS + Tailwind 3。方案 A 模块化单体。
- **交付里程碑**（spec §11）：P1 登录/用户/部门/客户/联系人/权限 → **P2 机会/看板/阶段历史** → P3 跟进记录/待办/首页三块 → P4 公海池 → P5 报表/Excel 导入 → P6 部署上线。spec 原话：**P1–P3 完成即可投入日常使用**。

## 5. 已定的架构约定（P2 必须沿用，不要另起一套）

1. **作用域单一入口**：`backend/app/db/scope.py` 的 `customer_query(actor)` 是所有客户读取的唯一入口（已含软删过滤）。`can_write_customer` / `assert_customer_writable` 负责写权限。**任何**返回客户相关数据的查询都必须从这里出发。
2. **错误体统一** `{code, message, detail}`；状态码口径：400 取值非法/口令弱、401 未认证、403 越权（**不是 404**）、404 不存在、409 数据冲突（`detail.similar`）、423 账号锁定。
3. **422 的 `detail[].input` 被全局剥离**（防止口令回显）。
4. **软删**：`deleted_at`，所有列表/详情过滤。
5. **口令**：`pwdlib` Argon2id（m=65536, t=3, p=4）；登录失败计数**落库**（`users.failed_login_count` / `locked_until`），因为线上跑 2 个 uvicorn worker，进程内缓存不共享。
6. **token**：access token 只在内存（120 分钟），refresh 走 `httpOnly; Secure=settings.cookie_secure; SameSite=Lax` cookie（7 天，`path=/api/v1/auth`）。
7. **`department_id` 的四个同步点**：创建客户、领取、分配/转移、**所属销售调整部门**（最后一条在 P1 修复轮 9 补齐：改用户部门时同事务更新其客户）。
8. **`last_activity_at` 的三条规则**：创建客户不写、编辑客户不碰、改联系人不动。
9. **查重只在调用者可见范围内匹配**（`customer_query(actor)` 打底）。跨部门重名不提示，这是有意的取舍，不要改回全表。
10. **命名**：Python snake_case；前端本地标识符 camelCase，但**镜像后端 wire 字段的 DTO 保持 snake_case**（写在 P1 计划的 Global Constraints 例外里）。
11. **数据库命名约定**在 `Base.metadata`（`pk_/uq_/ck_/fk_/ix_`）；`CheckConstraint` 必须显式 `name=`；函数索引必须显式命名。
12. **测试**：真实 PostgreSQL，每个测试重建 `public` schema；不许 SQLite；不许只断言状态码（要断言 `code` 字段）。

## 6. 已做裁定清单（避免重新讨论）

**认证与用户**
- 登录失败 5 次锁 15 分钟；不存在用户与错口令返回**同一** 401 文案与近似时序（decoy 哈希）。
- 密码重置清失败计数与锁定，但**不**自动解禁 `disabled` 账号。
- 未知角色 **fail-closed**：只见公海、全不可写；鉴权处直接 403。
- `manager` / `sales` 建号**必须带部门**（否则 400）。
- 管理员不能降级或停用自己（403）。

**客户与联系人**
- 公海客户（`owner_id IS NULL`）对销售与主管**可见但只读**；管理员可编辑。
- 销售**不能删除**客户（403「仅主管及以上可删除客户」）；spec 已回写。
- 管理员无部门 → 建的客户落公海，管理员可编辑；管理员不能把客户挂在自己名下（400）。
- 同客户下**主联系人至多一条、可为 0**；删主联系人不自动补位；部分唯一索引谓词含 `deleted_at IS NULL`。
- 客户/联系人 **软删**；重复删除 404；客户软删后其联系人经 `get_customer` 一律 404，联系人行保留。
- 查重名称归一化含 **NFKC 全角转半角**（为 Excel 导入准备）。
- `force=true` **只对当次请求生效**。

**接口形状**
- 联系人：`GET|POST /customers/{cid}/contacts` + `PATCH|DELETE /contacts/{id}`（无单条 GET，无嵌套写路由）。
- 联系人列表**不分页**（spec 已注明例外）。
- 客户列表分页体 `{items,total,page,page_size}`，`page_size ≤ 200`。
- `keyword` 覆盖客户名/简称/编码 **+ 该客户下未删除联系人的姓名/电话**；`date_from/date_to` 过滤 `last_activity_at`（半开区间，NULL 在有日期筛选时排除）。
- 列表枚举筛选非法值 → 400。

**其它**
- 工具链：依赖用下限（非 2024 年硬钉）；`uvicorn` 不带 `[standard]`；starlette TestClient 的 deprecation 接受。
- 前端**不做**负责人选择器（`GET /users` 仅管理员可读；负责人指派属 P2/P4 的分配 UI）。
- 前端无自动化测试框架（spec §12 已定：改用手测清单）。
- `tzdata` 已显式声明为后端依赖（`ZoneInfo` 需要，slim 镜像不带）。
- 仓库行尾统一 LF（新增 `.gitattributes`）。

## 7. 已知债务（P2/P3 时顺手还）

1. refresh token **无服务端吊销**（7 天绝对过期，cookie 可能比 token 活得久）。
2. 登录限流**依赖反向代理**（应用层没做）。
3. 登录失败计数是读-改-写，无行锁（并发下可能少计）。
4. 查重是全表取名字在 Python 侧比较（spec 决定不建索引）；**P5 Excel 导入上线前必须重评**。
5. 无 `audit_logs`（公海/分配 sprint 才需要）。
6. 前端无自动化测试；`CustomerDetailPage` 有 3 套状态机（客户编辑/联系人表单/删除确认）待拆——**等有前端测试再动**。
7. 弹窗缺焦点陷阱与背景滚动锁。
8. `contacts` 的 `IntegrityError → 409` 靠驱动异常文本匹配约束名（失效方向安全：回落 500）。
9. 部门同步只覆盖 `update_user` 一条写入路径；spec 提到的**每日一致性检查任务**未实现。
10. P1 的 `CustomerRead.owner_name` 用 `joinedload` + 关系 `lazy="raise"`（故意 fail-loud）：**以后任何读 `owner` 的新查询必须显式 `joinedload`**，否则 500。
11. `CustomerDetailPage` 的「不做负责人选择器」意味着主管无法在界面上把客户直接挂到下属名下（等 P4 分配 UI）。

## 8. P2 范围（spec 已定，不需要重新设计）

**三张表**：`opportunities`（§3.5）、`stage_histories`（§3.7）、`lost_reasons`（§3.10）。

**核心规则**
- 阶段固定四推进 + 两终态：`contact`(10%) → `needs`(30%) → `proposal`(50%) → `negotiation`(70%) → `won`(100%) / `lost`(0%)。
- 允许前进/后退/跨阶段跳转，**每次改阶段由 service 层强制写 `stage_histories`**（路由层不可绕）。
- 进 `lost` 必填 `lost_reason_id`；进 `won` 记 `won_at`；重开终态限 `manager`/`admin` 且必须选新阶段 + 填原因。
- **机会负责人与客户负责人一致**；客户领取/分配/转移时，同事务把未关闭机会一并改过去；**已赢/已输机会保留原负责人**（历史业绩归属）。
- 权限完全继承客户（能看客户 → 能看其机会；能写客户 → 能写机会）。

**接口**：`CRUD /api/v1/opportunities` + `POST /api/v1/opportunities/{id}/stage`。

**页面**：`/opportunities` 列表、`/opportunities/board` 看板（桌面拖拽改阶段，失败回弹；**手机端不做拖拽**，点卡片选阶段）。

**建议拆 9–10 个任务**：字典与种子 → 机会模型+迁移 → 阶段历史模型+迁移 → 机会 service（作用域/负责人同步/阶段变更） → 机会 API → 列表页 → 看板（含手机端） → 客户详情页嵌机会区 → 端到端验收。

**P2 明确不含**：跟进记录、待办、首页三块（P3）、报表（P5）、公海领取（P4）。所以做完 P2 能看到"谈到哪一步"，但还看不到"上次聊了什么、下次找谁"。

## 10. 工作方法论与纪律（照抄即可，别重新发明）

- **执行方式**：用户选定"子代理逐任务执行"。控制器（Lead）派单 → 实现者 → 独立评审者 → 修复轮 → 下一个任务。**一次只有一个实现者**（共享 git 索引）。
- **TDD 纪律**：先写失败测试并确认它真的红 → 实现 → 绿 → 提交。每个任务**必须**包含"改坏→红→改回→绿"的变异验证，并把红/绿原始输出写进报告。
- **评审纪律**：评审者不重跑测试、不连数据库、不派子代理；评审前**先建好评审包**（`task-N-review-package.md`，含 commit 列表 + diff stat + 完整 diff），不能让评审者自己去翻。
- **实现者/评审者一律不得再派子代理**（会失去可控性）。
- **派单纪律**：涉及既有 schema 的字段必须**从文档引用**，禁止凭记忆列举（P1 阶段因此错过一次：把 `owner_id` 写成必填，会让公海池在数据库层不可能存在）。派单里要写明"若我的说法与文档不符，请直接质疑"。
- **范围蔓延要挡**：判定标准是"spec 明文要求"，不是"看起来有用"。P1 挡掉过若干"顺手加个功能"。
- **账本**：每条裁定写进 `.superpowers/sdd/<plan>/progress.md`，并写"错的代价"。收尾时蒸馏进 `docs/`。
- **汇报习惯**：用户要求长任务期间主动同步进度，静默不超过约 10 分钟。
- **验收口径**：用户明确要求——测试必须压真实数据库语义、只断言状态码的测试不接受、**硬造假用户/假场景去测未实现的功能不接受**（比没有更坏，会带来虚假安全感）。
